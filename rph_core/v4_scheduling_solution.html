1. 事实确认摘要

经过对源码的逐级跟踪与分析，以下是对用户提出的五个论断的确认结果。

2. Variant 调度策略

2.1 现状分析

V4Orchestrator.run()
  └─ for each variant in variants:        ← 串行逐个执行
       ├─ CensoLiteEngine.run(smiles_A)   ← 独占 16 核
       ├─ checkpoint.mark(...)
       └─ CensoLiteEngine.run(smiles_B)   ← 等待 A 完成
⚠️ 资源浪费模式

variant_A 运行 B97 SP (10分钟) 时，variant_B 的 CREST (5分钟) 在等待。variant_A 结束后，variant_B 才开始 CREST。核心利用率低下。

2.2 解决思路：流水线并行

variant 级别的任务天然独立（不同 SMILES），但共享核心预算。不能简单多线程并行（会超售），而应使用 流水线调度：

时间 →
核心: ████████████████  16核

方案 A — 原始串行:
  variant_A: [CREST│B97 SP│mRRHO]
                                         variant_B: [CREST│B97 SP│mRRHO]
                    ↑ 16核空闲 ↑

方案 B — 流水线并行:
  variant_A: [CREST│B97 SP│mRRHO]
  variant_B:       [CREST│             B97 SP│mRRHO]
                    ↑ 共享16核 ↑
  variant_C:             [CREST│             B97 SP│mRRHO]

2.3 核心调度规则

#规则说明
1 全局任务队列 所有 variant 的所有可执行任务（CREST / ORCA SP / xTB mRRHO）放入一个共享优先队列
2 核心预算约束 任何时候 sum(active_cores) ≤ resources.nproc
3 优先级排序 CREST 搜索优先（通常更快，释放其他任务的依赖）；SP 可延后
4 任务就绪条件 只有前置依赖满足的任务才能出队执行
5 非抢占式 已开始的 QC 作业不中断

2.4 Variant 任务依赖 DAG

Variant_X:
  [CREST 搜索] ─→ [拆合] ─→ [能量解析] ─→ [Torsion去重] ─→ [预过滤]
                                                              │

3. 全局任务池调度引擎

3.1 架构概览

                         S1TaskScheduler
                              │
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
   [任务队列]           [核心预算管理器]      [进度追踪器]

3.2 核心数据结构

@dataclass
class S1Task:
    task_id: str                    # "variant:step:index"
    variant_id: str
    step: str                       # "crest_search" | "b97_sp" | "mrrho"
    priority: int                   # 0=CREST, 1=B97, 2=mRRHO
    cores_required: int             # 任务需要的核数
    estimated_duration: float       # 历史预估 (秒)
    dependencies: List[str]         # 前置 task_id 列表
    state: TaskState                # pending | running | completed | failed
    submit_fn: Callable             # 实际执行函数
    result: Any                     # 执行结果
    submitted_at: Optional[float]
    completed_at: Optional[float]

3.3 调度算法

class S1TaskScheduler:
    def __init__(self, total_cores: int = 16):
        self.total_cores = total_cores
        self.active_cores = 0
        self.pending: List[S1Task] = []      # 优先级队列 (heapq)
        self.running: Dict[str, S1Task] = {}
        self.completed: Dict[str, Any] = {}
        self.pool = ThreadPoolExecutor(max_workers=total_cores * 2)

    def submit_all(self, tasks: List[S1Task]):
        """一次性提交所有 variant 的所有任务"""
        for task in tasks:
            heapq.heappush(self.pending, (-task.priority, task))

    def schedule_cycle(self) -> None:
        """调度循环 — 每次完成一个任务后调用"""
        while self.pending and self._can_dispatch(self.pending[0]):
            _, task = heapq.heappop(self.pending)
            if not self._dependencies_met(task):
                heapq.heappush(self.pending, (_, task))
                break
            self._dispatch(task)

    def _can_dispatch(self, task: S1Task) -> bool:
        return self.active_cores + task.cores_required <= self.total_cores

4.1 现状问题

当前 S1 checkpoint 签名包含 整个 config.step1 配置树（仅过滤了少数调度键）：

s1_signature = V4Checkpoint.signature({
    "config": self.config.get("step1", {}),  # ← 几乎全部 step1 配置
    "executables": { "crest": "/usr/bin/crest", ... },  # ← 绝对路径

4.4 resume_policy 三档行为

策略签名匹配签名不匹配
strict (默认) 复用 抛出 ResumeCheckpointError，要求 --recompute-from
recompute 复用 自动从签名变化的第一步开始重新计算
use-existing-upstream 复用 保留已有结果（忽略签名变化），仅对新任务使用新配置
💡 配置项
run:
  resume_policy: strict            # strict | recompute | use-existing-upstream
  checkpoint:
    enabled: true
    granularity: tiered            # flat (整个stage) | tiered (per-step)
