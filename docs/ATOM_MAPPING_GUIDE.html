原子映射方案

SMILES · Map Number · XYZ 三索引空间的对齐与回退链 · 最后更新 2026-07-06

1. 概览

原子映射解决一个核心问题：把 S0 在 SMILES 上识别出的"成键原子对"翻译成 S2 在 xyz 几何上能直接操作的原子下标。S0 的输出是 forming_bonds = [[1,11],[3,8]] 这样的 map_number 对；S2 的 xTB 扫描必须知道这两个数对应 xyz 文件里的第几行原子。中间的转换桥梁就是 atom_map_xyz.json。

一句话定位 原子映射 = "把 S0 的化学认知对齐到 S1 的几何现实" 的过程。映射质量直接决定 S2 retro_scan 能否启动。

设计目标

  • 多源冗余：Kabsch 几何对齐 → SubstructMatch 图匹配 → SMARTS 拓扑识别，三道闸门层层兜底
  • 可审计：每条映射都带 provenance（来源、置信度、是否完整），下游可据此决定是否信任
  • 安全失败：映射失败不会污染下游，_is_xyz_mapping_usable 闸门会拒绝低质映射，强制走 SMARTS 兜底

2. 三种索引空间

整个映射方案绕着三套原子编号转，理清它们的关系是理解所有代码的前提：

SMILES idx
0, 1, 2, …
RDKit Chem.MolFromSmiles 解析顺序
同分子不同 SMILES 写法会得到不同 idx
Map Number
1, 2, 3, …
S0 机制分类器赋予的规范编号
写入 [C:1] 形式的 mapped SMILES；反应类型确定后稳定不变
XYZ idx
0, 1, 2, …
xyz 文件里的物理行号（含 H、含 Lewis 酸）
由构象生成器（XTB / Gaussian）的输出顺序决定，不可控

转换链

SMILES idx  ──(S0: atom_map_smiles.json)──▶  Map Number
                                                      │
                                                      │  ❗ 这一步是 atom_map_xyz.json 的职责
                                                      ▼
                                                   XYZ idx
                                                      ▲
                                                      │
SMILES idx  ──(S1: smiles_to_xyz_map.json)────────────┘
                                                      │
                              （另一条独立的桥，但 S2 不直接使用）
设计疏漏 S1 阶段产出的 smiles_to_xyz_map.json 已经记录了 SMILES idx → XYZ idx 的对应（构象生成时由 RDKit 写入），S0 阶段的 atom_map_smiles.json 又有 SMILES idx → Map Number。两条独立桥本可无需 Kabsch直接组合出 Map Number → XYZ idx，但当前 S2 的解析链完全绕开了这条路径，只走 Kabsch/SubstructMatch。

S1→S2 关键交接物：atom_map_xyz.json

这个 JSON 是整个映射系统的核心交付物，由 _build_and_save_xyz_mapping() 在 S1 完成后写入。S2 通过它（结合 S0 的 mechanism_summary）就能直接拿到 xyz_idx 形式的 forming_bonds。

字段类型含义
map_to_product_xyz_1based Dict[str, int] 核心映射：Map Number → 产物 xyz 行号（1-based）
map_to_precursor_xyz_1based Dict[str, int] 同上，针对前体（如果存在）
forming_bonds_full_notation List[Dict] S0 的 forming_bonds 已翻译成 xyz_idx；
每项含 map_space / product_xyz_1based / bond_type_*
provenance Dict 来源标记（详见 §8），决定下游是否信任此映射

顺序来源输入失败时
P1 atom_map_xyz.json 的 forming_bonds_full_notation Kabsch 已翻译好的 xyz_idx 对 返回 tuple()，进 P2
P2 S0/S1 注解（forming_bonds_annotated） map_space + map_to_product_xyz 翻译 返回 tuple()，进 P3

关键观察 P1/P2/P3 全部依赖 atom_map_xyz.json。一旦该映射被判定不可用（来源不在白名单），三个解析器整体跳过，直接进入 SMARTS 兜底。换言之，整个映射系统的最薄弱环节就是 atom_map_xyz 的生成质量。

5. Kabsch + Hungarian：主路径

_build_mol_to_xyz_index_mapping()

（orchestrator.py:1547）的核心算法。

五步流程

mapped_smiles ──Chem.MolFromSmiles──▶ RDKit Mol
                                          │
                                          ▼  rdDistGeom.EmbedMolecule
                                     3D 参考构象 (EETKP)
                                          │
                          ┌───────────────┴────────────────┐
                          ▼                                 ▼
                  RDKit 坐标 (N×3)               XYZ 坐标 (M×3, M≥N)
                          │                                 │
                          │           heavy_mask ← NON_ORGANIC_XYZ_ELEMENTS
                          │           {H, Li, Cl, Na, K, Br, I, Mg, Al}
                          │                                 │
                          └──────────────┬──────────────────┘
                                         ▼
                              ★ Kabsch 最优重叠（最小化 RMSD）
                                         │
                                         ▼
                            ★ Hungarian 按元素分组二分匹配
                                         │
                                         ▼
                              mol_to_xyz: {rdkit_idx: xyz_idx}
                                         │
                                         ▼
                          ┌──────────────┴──────────────────┐
                          ▼                                 ▼
                  计算每对残差 ‖Δr‖                  元素一致性校验
                          │                                 │
                          ▼                                 │
              ┌─────────────────────────┐                  │
              │  rmsd ≤ 2.0 Å ?         │                  │
              │  max_err ≤ 3.0 Å ?      │                  │
              └────────────┬────────────┘                  │
                  两条件都满足 │ 任一不满足                    │
                           ▼  └─────────────────────────────┐
        ✓ 返回 kabsch_hungarian / high      │
                                                      ▼
                                          ↓ 走 SubstructMatch 兜底

两个阈值的含义

指标阈值含义典型失败场景
rmsd ≤ 2.0 Å 所有原子平均偏差 整体构象选错（如取到了能量略高的次优构象）
max_err ≤ 3.0 Å 单个原子最大偏差 柔性取代基旋转（如苄基、Cbz 苯环）；通常 rmsd 仍合格
设计语义 两个阈值必须同时满足才放行。RMSD 防整体跑偏，max_err 防局部柔性取代基拖累。max_err 是更严格的闸门——大部分失败是 max_err 超 3.0 而 rmsd 合格。

NON_ORGANIC_XYZ_ELEMENTS：重金属过滤白名单

# rph_core/utils/cleaner_adapter.py:16
NON_ORGANIC_XYZ_ELEMENTS = frozenset({'H', 'Li', 'Cl', 'Na', 'K', 'Br', 'I', 'Mg', 'Al'})

Kabsch 对齐前会把 xyz 里的这些元素剔除，只保留有机重原子参与对齐。Mg/Cl 等 Lewis 酸原子不会污染几何对齐本身——但下游的 build_bond_graph 仍会因缺金属半径而炸（见 §10）。

6. SubstructMatch 兜底

Kabsch 失败后立即调用 get_map_to_xyz_dict()（cleaner_adapter.py:344）。

四步流程

mapped_smiles (带 [C:1] 编号)
        │
        ▼  Chem.MolFromSmiles（去掉 map number）
   query_mol (拓扑图)
        │
        ▼  读取 xyz → MolFromXYZBlock → DetermineBonds
   xyz_mol (RDKit 自动感知连接性)
        │
        ▼  xyz_mol.GetSubstructMatches(query_mol, uniquify=False)
        │
        ├── 命中 ──▶ 取第一个 match，按 map_number 还原 mol_to_xyz
        │           ✓ 返回 {smiles_idx: xyz_idx}
        │
        └── 0 命中 ──▶ useChirality=True 再试一次
                │
                ├── 命中 ──▶ 返回
                │
                └── 仍 0 命中 ──▶ ✗ 返回 {}，日志:
                                  "Caller should use SMARTS / graph-isomorphism fallback"
代码注释 vs 真实情况 日志里的 "graph-isomorphism fallback" 字样极具误导性。全代码库 grep 该字符串仅此一处出现——根本没有独立的图同构算法。实际接住的只有 SMARTSMatcher 拓扑识别。这条日志是 5 年前的 TODO 痕迹。

典型失败原因

  • rdDetermineBonds.DetermineBonds 从纯坐标反推连接性时，对杂环/桥环/张力键的键序感知与 SMILES 不一致
  • 反应中心成键/断键导致 query 与 xyz 的图结构略有差异（虽然对产物而言应该相同）
  • 立体化学 chirality flag 不匹配（fallback 时关闭 chirality 通常能救回）

9. 可用性闸门：_is_xyz_mapping_usable

所有 P1/P2/P3 解析器的前置守卫（orchestrator.py:1294）。一个 20 行的纯函数，但决定整个映射系统的命运。

def _is_xyz_mapping_usable(xyz_mapping_payload: Optional[Dict[str, Any]]) -> bool:
    if not isinstance(xyz_mapping_payload, dict):
        return False
    provenance = xyz_mapping_payload.get("provenance")
    if not isinstance(provenance, dict):
        return False
    source = str(provenance.get("mapping_source", "")).strip().lower()
    confidence = str(provenance.get("confidence", "none")).strip().lower()

    # 黑名单：明确拒绝
    rejected_sources = {"substructure_match", "_smilesatomoutputorder",
                        "assumed_heavy_order", "legacy", "empty"}
    if source in rejected_sources:
        return False

    # 白名单：有条件接受
    if source == "atom_map_sidecar":
        return bool(provenance.get("validated", False))
    if source == "kabsch_hungarian":
        return confidence == "high"
    return False   # 未知 source 一律拒绝
语义总结 只有 kabsch_hungarian + high 或 atom_map_sidecar + validated 两种组合能通过。这导致一个反直觉的结果：SubstructMatch 即使成功也不被信任——这条路径产出的映射会被直接丢弃，转而走 SMARTS。

10. 已知陷阱与失败模式

① 柔性取代基击穿 Kabsch max_err

典型触发
Cbz / Bn / TBDMS / 烷基链等可绕单键自由旋转的基团
症状
rmsd ≈ 1.5 Å 合格
max_err ≈ 3.7~5.0 Å 超阈
后果
Kabsch 失败 → 走 SubstructMatch → 也常失败 → 走 SMARTS

② "graph-isomorphism fallback" 是幽灵代码

cleaner_adapter.py:420 的日志承诺"Caller should use SMARTS / graph-isomorphism fallback"，但全代码库无任何图同构算法实现。真正的兜底是 SMARTSMatcher 的拓扑识别。看到这条日志不要去找图同构代码——它不存在。

③ molecular_graph.COVALENT_RADII 缺金属

# rph_core/utils/molecular_graph.py:22
COVALENT_RADII = {
    'H': 0.31, 'B': 0.85, 'C': 0.76, 'N': 0.71, 'O': 0.66,
    'F': 0.57, 'Si': 1.11, 'P': 1.07, 'S': 1.05,
    'Cl': 1.02, 'Br': 1.20, 'I': 1.39
}   # ← 没有 Mg / Li / Zn / Na / K / Ca / Al ...

所有 Lewis 酸反应在 build_bond_graph() 调用处都会抛 Unknown element radius: O, Mg。该错误被 retro_scan 捕获并标 DEGRADED，由 path_search 救回。但这意味着：

  • SMARTS 兜底若依赖 build_bond_graph，对 LA 反应必然失败
  • LA 模式下 SMARTSMatcher 切换到 MolFromSmiles 构造 Mol 以绕开此问题
  • 但 geometry_guard.py 中的多次 build_bond_graph 调用仍会失败

④ SMILES 桥被绕开

如 §2 所述，smiles_to_xyz_map.json + atom_map_smiles.json 已隐含完整的 map_number → xyz_idx 映射，但解析链从不读取这两条桥的组合。这是当前方案最大的设计疏漏。
