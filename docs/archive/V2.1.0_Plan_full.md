## 1. 执行摘要

当前仓库并不是“V2.1.0 完全未开始”，而是处于 **协议入口已接入、配置已铺开、S2 fallback 已落地、S4 降级已成熟，但 S1 协议层实体与 `final_opt_sp` 真实闭环尚未完成** 的阶段。

从真实代码看，V2.1.0 的发布阻塞点集中在三件事：

1. `rph_core/steps/conformer_search/pipeline/stages/final_opt_sp.py` 仍是 10 行透传壳子；
2. `rph_core/steps/conformer_search/` 只有 pipeline 目录骨架，没有 `ProtocolSpec / PipelineExecutor` 实体；
3. `rph_core/steps/anchor/handler.py` 写出的 provenance 仍停留在 `phase3a` 语义，尚未表达最终的 protocol/stage 元数据。

因此，V2.1.0 的正确推进方式不是“全面重构”，而是按以下顺序收口：

- **Phase 1**：补协议层最小实体，冻结文件边界
- **Phase 2**：把 `final_opt_sp` 从壳子改成真正的 stage
- **Phase 3**：完成 lite 主闭环，确认 S2/S4 接口语义
- **Phase 4**：补 zero、测试、版本、README、报告收口

1. 把 `final_opt_sp` 做成真正的 stage，而不是透传 wrapper

3. 大改 S2/S3 算法主流程
4. 重构 S4 全部 extractor 体系

## 6. Phase 1 详细方案：补齐协议层最小实体

### 6.1 Phase 目标

让 lite/zero 的存在不再只依赖“改配置后塞回 `ConformerEngine`”，而是有最小可读、可测试、可追踪的协议层对象。

### 6.2 Phase 1 必改文件与操作清单

#### 1) `rph_core/steps/conformer_search/protocols.py`（新增）

**目标**：定义 V2.1.0 最小协议描述对象。

**建议内容**：

- 新增 `ProtocolSpec`（推荐 dataclass）
- 至少包含以下字段：
  - `name`
  - `two_stage_enabled`
  - `ngeom_default`
  - `ngeom_max`
  - `final_opt_sp_enabled`
  - `freq_enabled`
  - `final_sp_enabled`
  - `selection_mode`
  - `provenance_flags`
  - `raw_config`
- 新增 `resolve_protocol_spec(config: Dict[str, Any], protocol: str) -> ProtocolSpec`
- `ext/default` 返回“兼容既有主路径”的 spec，`lite/zero` 返回轻量 spec

**修改原因**：

- 当前 protocol 语义散落在 `engine_factory.py`、`engine.py`、`handler.py`、`defaults.yaml`
- 没有协议对象，就无法稳定写 provenance，也无法给测试明确契约对象

**依赖**：无

**验收点**：

- 能从 `config/defaults.yaml` 正确解析 `lite` 与 `zero`
- `ProtocolSpec` 不引入新 QC 执行逻辑，只表达协议语义

#### 2) `rph_core/steps/conformer_search/pipeline.py`（新增）

**目标**：新增最小 pipeline 桥接器，而不是完整 DAG。

**建议内容**：

- 新增 `PipelineExecutor` 或 `ProtocolExecutionPlan`
- 负责：
  - 持有 `ProtocolSpec`
  - 生成 stage 顺序描述
  - 暴露给 `ConformerEngine` 使用的最小执行入口
- 允许实现形式为：
  - `ProtocolSpec -> PipelineExecutor -> final_opt_sp`，或
  - `ProtocolSpec -> EngineBridge -> final_opt_sp`

**修改原因**：

- 需要一个真实存在的“协议层实体”，以支撑 V2.1.0 的版本语义
- 但又不能为了收口版引入高风险全面重构

**依赖**：`protocols.py`

**验收点**：

- 不重写 `ConformerEngine`
- 能表达 lite/zero 与 ext 的执行语义差异

#### 3) `rph_core/steps/conformer_search/pipeline/__init__.py`（小改）

**目标**：导出协议层最小公共接口。

**建议修改**：

- 导出 `ProtocolSpec`
- 导出 `resolve_protocol_spec`
- 导出 `PipelineExecutor` 或等价入口

#### 4) `rph_core/steps/conformer_search/pipeline/stages/__init__.py`（小改）

**目标**：把 `final_opt_sp` stage 变成正式导出对象，而不是目录占位。

**建议修改**：

- 导出 `execute_final_opt_sp`
- 如果 Phase 2 采用 dataclass stage model，则同步导出 stage 结果类型

#### 5) `rph_core/steps/anchor/engine_factory.py`（小改）

**当前真实状态**：

- 已根据 protocol 合并 config
- lite/zero 行为通过 `_build_protocol_config()` 下沉

**Phase 1 修改目标**：

- 在不破坏 ext/default 的前提下，接入 `resolve_protocol_spec()`
- 明确 `create_s1_engine()` 的职责边界：
  - 负责 protocol 归一化
  - 负责 spec 解析
  - 负责最小 config 注入
  - 不负责直接实现 pipeline 行为

**建议修改点**：

- 保留 `_build_protocol_config()`，但让其成为协议解析后的兼容下沉步骤
- 让测试既能断言 config 压缩，也能断言 spec 解析

#### 6) `config/defaults.yaml`（小改）

**Phase 1 修改目标**：

- 对 `step1.protocol_stack.lite.final_opt_sp` 与 `zero.final_opt_sp` 的字段做注释校准
- 如当前代码需要，引入明确字段：
  - `selection_mode`
  - `write_stage_meta`
  - `write_provenance_flags`

**注意**：

- 只做 schema/命名整理，不另起新配置文件
- 继续保持 `defaults.yaml` 单一事实源

#### 7) `tests/test_step1_protocol_factory.py`（扩展）

**Phase 1 目标**：把当前“工厂能创建 engine”升级为“协议对象 + provenance 基线”测试。

**需要新增的断言**：

- lite/zero 的 `ProtocolSpec` 解析结果
- `final_opt_sp.enabled/freq` 与 config 一致
- provenance 中不再仅有 `phase3a` 占位命名

#### 8) `tests/test_step1_protocol_contract.py`（新增）

**目标**：新增协议层契约测试。

**建议覆盖范围**：

- `ext/default/lite/zero` 解析结果
- `unknown/full` 的失败行为
- spec 到 engine config 的映射边界

### 6.3 Phase 1 退出标准

- `ProtocolSpec` 存在且有测试
- pipeline 最小执行桥接存在
- ext/default 路径行为不变
- lite/zero 不再只是“参数名义存在”，而是有协议对象表达

## 7. Phase 2 详细方案：实现真正的 `final_opt_sp` stage

### 7.1 Phase 目标

把当前只有 `return runner(candidates)` 的 `final_opt_sp` 壳子，改成带有明确输入、选择、执行与输出元数据的阶段实现。这是整个 V2.1.0 的最高优先级代码缺口。

### 7.2 Phase 2 必改文件与操作清单

#### 1) `rph_core/steps/conformer_search/pipeline/stages/final_opt_sp.py`（重点修改）

**当前真实状态**：

```python
def execute_final_opt_sp(...):
    return runner(candidates)
```

**Phase 2 目标状态**：

- 输入明确：筛选后的 conformer candidate 列表
- 行为明确：
  - 候选标准化
  - 选择模式记录
  - 是否做 freq 的记录
  - 是否做最终 SP 的记录
  - 结果与 stage meta 一起返回
- 输出明确：
  - `best_log` / `best_result_path`
  - `best_energy`
  - `stage_meta`

**推荐实现方式**：

- 新增 `FinalOptSPResult`（dataclass）
- `execute_final_opt_sp()` 入参增加 `protocol_spec` 或 `stage_config`
- 在不绕开 `runner` 的前提下，写清：
  - `selected_candidate_count`
  - `freq_requested`
  - `final_sp_requested`
  - `selection_mode`
  - `protocol`

**必须避免**：

- 新起 subprocess 路径直接跑 Gaussian/ORCA
- 复制一套平行 QC 执行器
- 把 ext 默认流程与 lite/zero 分叉成两套无法维护的主逻辑

#### 2) `rph_core/steps/conformer_search/engine.py`（中改）

**当前真实状态**：

- `_run_final_opt_sp_stage()` 已 emit 进度事件
- 调用 `execute_final_opt_sp(candidates=selected, runner=self._step_dft_opt_sp_coupled)`

**Phase 2 修改目标**：

- 把 `ProtocolSpec` 传入 stage
- 接收 `FinalOptSPResult` 或等价结果对象
- 将 stage meta 回写到 engine 级状态/progress 事件
- `run()` 与 `run_optimization_only()` 共享同一 stage 语义

**建议修改点**：

- 在 `__init__` 中缓存 protocol spec
- `_run_final_opt_sp_stage()` 返回 `(best_log, best_energy, stage_meta)` 或结果对象
- 将 `freq_requested` 从当前直接读 config，改成统一从 spec/stage_meta 读取

#### 3) `rph_core/steps/anchor/handler.py`（中改）

**当前真实状态**：

- provenance 固定写：
  - `has_geometry_optimization: True`
  - `final_opt_sp.enabled = protocol in {lite, zero}`
  - `phase = phase3a / ext_default`

**Phase 2 修改目标**：

- provenance 不再写抽象阶段名，而是写真实 stage 元数据
- 至少补充：
  - `final_opt_sp.enabled`
  - `final_opt_sp.freq_requested`
  - `final_opt_sp.final_sp_requested`
  - `final_opt_sp.selection_mode`
  - `final_opt_sp.stage_status`
  - `has_geometry_optimization`

**原因**：

- S2 fallback 与 S4 降级都依赖 provenance 语义
- 继续沿用 `phase3a` 占位命名会让 Phase 3/4 验收失真

#### 4) `tests/test_step1_final_opt_sp.py`（新增）

**目标**：给 `final_opt_sp` stage 建立真正的单元测试边界。

**建议测试项**：

- 输入候选为空时的失败策略
- 输入候选为 1 个时的行为
- `freq=True/False` 的 stage meta 区分
- `selection_mode` 写入结果
- runner 被调用次数与入参规范

#### 5) `tests/test_step1_protocol_factory.py`（扩展）

**补充断言**：

- lite provenance 不再只是 `phase3a`
- zero provenance 中能清楚表达“有几何优化、但不请求频率”

### 7.3 Phase 2 退出标准

- `final_opt_sp` 不再是透传函数
- `engine.py` 与 `handler.py` 能消费 stage 元数据
- 单测能证明 lite/zero 的 final stage 语义差异

## 11. 推荐实施顺序与依赖关系

### 11.1 强依赖顺序

   - 不先补 `final_opt_sp`，Phase 3 的 lite 主闭环永远是伪闭环

   - 验证 S2 fallback 与 S4 降级是否真的与协议语义一致
4. **最后做 Phase 4**
   - 所有文档、版本、发布动作都应该建立在闭环已证实的基础上

### 11.2 不建议的错误顺序

- 先改 README，再补代码
- 先把版本号改到 2.1.0，再补 final stage
- 先大量新建测试，再不修 provenance 语义
